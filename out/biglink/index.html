SECTION 04 · HIERARCHICAL CONTEXT MEMORY (P-114)

三层分级上下文记忆（L1 短期滑窗 + L2 中期确定性摘要 + L3 长期用户偏好）

互动沙盘 #2 · 零额外 LLM 调用的确定性压缩

面试官常问：“长对话超过几十轮后 Token 爆炸怎么办？如果用大模型自动 Summarize 历史，万一总结错了税额或把旧审批当成新授权怎么办？”
Biglink 在 runtime-service/src/biglink_runtime/memory.py 中实现了确定性三层分级记忆（Hierarchical Context Memory）：不消耗额外 LLM 摘要 Token，且强制打上 authority="context_only_not_approval" 烙印，严格区分“对话上下文参考”与“持久授权/写操作审批真值”。

三层记忆动态压缩沙盘（拖动对话轮次滑块观察 L1/L2/L3 内存分布）
Tier 1 · 短期工作记忆 (Working) 保留最近 8 条 (4,000 chars)

直接截取最近 TIER1_RECENT_LIMIT=8 条完整对话原文（上限 4,000 字符），保证指代消解（如“那这家企业上月呢？”）100% 精准。 

[Turn 21..28] 保留完整 User/Assistant 原文
Token 占用恒定: ~1,150 tokens (不随总轮次线性膨胀)
Tier 2 · 中期情景与台账摘要 (Episodic) 已折叠 20 条旧对话 + 5 条任务里程碑

两部分合成：① 滑出窗口的旧消息提取关键实体（税号、期间 YYYY-MM、领域关键词）；② 从 main-service 拉取最近 5 个持久任务的确定性状态里程碑（1,600 字符上限）。

落盘在 main-service 的 user_preferences 表（最多 16 项、90 天过期），支持正则自动提炼（如“记住默认期间 2026-10”）与前端工作台手动增删。

SECTION 05 · MULTI-AGENT A2A & PER-GOAL INTENT MODE DAG (P-116)

多 Agent 协同：A2A 跨6域任务图（TaskGraph）与细粒度读写权限下传

互动沙盘 #3 · 解决复合指令“一刀切权限”难题

当用户发出一句跨领域复合指令，例如：“先帮我查一下这个月的销项发票汇总，再根据发票数据准备增值税申报草稿，最后扫一下税务风险”，系统如何拆解并防止只读子任务越权执行写操作？
我们在 IntentDecision.sub_goals 与 TaskGraph 中实现了子目标级独立意图模式（Per-Goal Intent Mode，`P-116`）与上游依赖产物注入（`graphDependencies`）。

多 Agent 有向无环图 (DAG) 调度与 2-Slot 租约模拟器
🤖 Node A: Invoice Agent business_query (只读)

子目标：查询 2026-10 销项与进项发票汇总
依赖节点：无（入度 = 0，立即领取 Slot #1）
权限围栏：intent_mode="business_query"，Catalog 强制拦截任何开票/作废/红冲写工具。 

状态: ready → running (Worker Slot #1)
输出:销项税额 ¥18,420 / 进项税额 ¥6,100
🤖 Node B: Risk Agent business_query (只读)

子目标：扫描当期增值税税负率异常风险
依赖节点：无（入度 = 0，并行领取 Slot #2）
并发控制：同一企业最多 2 个并发 Worker 槽位，兼顾吞吐与税局防封控。 

状态: ready → running (Worker Slot #2)
输出: 税负率 2.1%，无重大风险预警
🤖 Node C: Tax Agent business_prepare (仅草稿)

子目标：根据发票汇总生成增值税申报草稿
依赖节点：dependsOn: ["Node A"]
产物传递：Node A 完成后，其发票汇总通过 graphDependencies 注入 Tax Agent 的 /plan。 

状态: blocked_by_dep → waiting_approval
围栏: 生成算税草稿(draftHash)，禁止自动扣款
▶ 阶段 ①：云端大模型结构化拆解跨 6 域子目标并赋予细粒度权限
传统多 Agent 框架往往把整句用户请求共享同一个权限模式（要么全只读导致没法建申报草稿，要么全放开导致查发票子 Agent 误调写接口）。
Biglink 在 IntentSubGoal 契约中为每个子目标单独定义 intent_mode：Node A 与 Node B 锁死为 business_query，Node C 设为 business_prepare，由 TaskGraph 写入各自持久任务的 task.context["intentMode"]。

    { "id": "g3", "domain": "tax",     "intentMode": "business_prepare", "dependsOn": ["g1"] }
  ]

SECTION 06 · WRITE-SAFETY STATE MACHINE, CAS FENCING & GOVERNANCE

12态持久状态机、草稿哈希绑定、半开单探测熔断与根任务预算台账

互动沙盘 #4 · 金融财税级防重放与故障自愈

财税 Agent 最怕两件事：① 未经会计确认就真报税/真开票；② 调税局接口网络超时（结果未知），Agent 傻傻自动重试导致重复开票或重复扣税。 点击下方 4 个核心安全机制演示按钮，查看 Biglink 如何在代码层彻底封死这些风险。

高危写安全与治理机制交互演示器

🔒 机制 1：内容绑定确认（Draft Hash + Approval Token + boundTaskId）

痛点：如果用户在聊天框说“确认提交”，怎么保证他确认的是刚才那份 ¥12,300 的增值税草稿，而不是并发修改后的另一份草稿？

Biglink 源码级实现：

  • 当任务进入 waiting_approval 时，对草稿的关键业务字段（税种、期间、纳税人识别号、应补退税额、发票明细）做规范化 JSON 排序并计算 draftHash = SHA256(canonical_draft)。
  • 前端审批卡片在打开瞬间锁定 boundTaskId（P-114），即使会计在旁边的聊天框切换了会话，点击“确认申报”时依然精确投递给原任务。
  • tools-service 在真正发起 MCP 写调用前，二次比对 approval.draftHash == current_draft.draftHash，任何一字节篡改直接拒绝执行并打回重审。

🧬 1. 为什么本地微调基座选 Gemma-2-9B-IT（含 Gemma-3-12B 演进）？ Model Selection
  • 参数量处于“单卡甜点区（Sweet Spot）”：70B 模型需要多卡张量并行（TP>=2），硬件成本高出 4 倍；而 2B/3B 小模型在解释复杂增值税/企业所得税口径时容易出现逻辑跳步。9B 参数量在 FP16/BF16 下仅占约 18GB 显存（AWQ INT4 量化后仅 6.2GB），单张 24GB/48GB 显卡即可轻松塞下并留出充裕的 KV Cache。
  • 架构优势（滑动窗口注意力 + Logit Soft-Capping）：Gemma-2 采用局部滑动窗口注意力（Sliding Window Attention）与全局注意力交替结构，配合知识蒸馏预训练，在同等 9B 量级中指令遵循度（Instruction Following）与拒答边界稳定性显著优于早期 7B 模型。
  • 垂域 LoRA 微调配方（1.8 万条高质量样本）：
    • 数据集构成：10,000 条脱敏财税政策问答（小规模/一般纳税人、专票冲红、汇算清缴口径）+ 4,500 条 Biglink 工作台操作引导 + 3,500 条负样本拒答训练（防越权承诺）。
    • 关键边界训练：强制微调模型在遇到“帮我直接把税报了”但误入闲聊通道时，绝不伪造“已为您申报成功”的幻觉回复，而是引导进入受控业务工作台。
    • 训练超参：基于 LLaMA-Factory，LoRA rank=16, alpha=32，target q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj，单张 48GB 卡 3.5 小时完成 3 Epochs 收敛。

面试官常问：“你们拆了 runtime、main、tools 三个服务，又有三层记忆、又有状态机和子进程 Worker，服务负担会不会很重？用了多少个集群节点？” 回答的核心原则是：控制面极轻（纯异步 I/O + 零 LLM 记忆压缩），算力与重 I/O 隔离，50 人公司的千万级利润产品只需要「1 个生产可用区集群（共 5 台核心实例）」即可稳稳扛住峰值！

🪶 1. 为什么这套架构的服务负担（Overhead）极低？ Low Overhead
  • 三服务内部通信零序列化膨胀：runtime ↔ main ↔ tools 走同机/同内网 VPC 高速回环，且复用持久 httpx.AsyncClient 连接池（P-123），单次跨服务 RPC 开销仅 0.8ms ~ 1.5ms，相比大模型动辄 500ms+ 的推理耗时占比不到 0.3%。
  • 三层记忆组装是纯 CPU 确定性算法：memory.py 采用滑窗截断 + 正则实体提取 + SQLite/MySQL 主键查询，单次组装耗时 < 3.5ms，不额外发起任何 LLM 摘要请求。
  • 异步事件循环与线程池 Offload 解耦：FastAPI 主协程只负责高并发 SSE 流转发与轻量路由；同步 DB 操作通过 offload() 放入受控线程池，防止慢 SQL 阻塞事件循环（P-080）。
  • 按需拉起业务子进程 + 2-Slot 背压限流：只有真正进入企享云 MCP 执行阶段才领取 Worker 槽位（每企业上限 2 个），天然形成上游反压（Backpressure），绝不会因为瞬间涌入几百个查询任务而打爆内存。

第二是复杂跨领域协同与权限失控的矛盾：我们基于 AgentScope 2.0 拆分为 runtime / main / tools 三个零信任隔离服务，在 main-service 实现了 A2A 多 Agent 有向无环图（TaskGraph），并且为每个子目标单独绑定细粒度的 intent_mode（例如查发票节点锁死为只读 business_query，报税节点设为草稿态 business_prepare），配合上游依赖产物 graphDependencies 传递，防止子任务越权。
第三是高危财税写操作的幂等与防重放：我们实现了 12 态 CAS 持久状态机、草稿 SHA-256 哈希绑定审批、executionVersion 围栏以及 outcome_unknown 未知结果只对账不盲目重试机制，做到全年写操作零事故。”

【标准回答话术】：

  • 为什么混用：财税 SaaS 用户每天有大量诸如此类的提问——“小规模季度免税额度多少？”、“怎么在右上角切换企业？”。如果全部调用云端大模型并带上全套业务 Schema，不仅首字延迟高达 800ms+，而且每年要多烧掉五十多万 Token 费。用 1.8 万条财税垂域样本对 Gemma-2-9B-IT 做 LoRA 微调后，部署在单卡 L20 的 vLLM 上，这类非事务问答 TTFT 只要 140ms，边际成本趋近于 0。
  • 怎么防止 JEV 误判（双保险纠偏机制）：
    1. 第一重防护（启发式后置纠偏 `post_validate_intent`）：即使前置分类器或模型输出了 chat，只要我们的确定性规则检测器发现用户原话里包含明确的企业动作词（如“申报、开票、红冲、算税、风险扫描、查今年发票”），代码层会强制将意图修正升级为 business_* 并转入受控业务流。
    2. 第二重防护（微调负样本护栏）：本地 Gemma 模型在微调时注入了 3,500 条边界拒答样本，且物理进程上没有任何 MCP 工具调用权限；即便漏网的业务请求落到本地模型，它也只会回复引导卡片，绝不可能伪造“已帮您申报成功”的假结果。

“我们在 runtime-service/memory.py 里实现了三层分级上下文架构：
1. L1 短期工作记忆（Working Memory）：保留当前会话最近 8 条完整消息（硬上限 4,000 字符），保证会计连续追问‘那上个月呢？’时指代消解不断裂。
2. L2 中期情景与台账摘要（Episodic & Ledger Digest）：当对话超过 8 条时，滑出窗口的旧消息通过确定性正则提取出讨论过的税期（如 2026-09）、税号和领域标签；同时向 main-service 拉取该企业最近 5 个持久业务任务的真实状态与摘要（上限 1,600 字符）。
3. L3 长期用户偏好（Long-Term Preferences）：存储在 main-service 的 SQLite/MySQL user_preferences 表中（上限 16 项，TTL 90 天），记录用户偏好的默认税期、常用业务域和汇报风格。
为什么不用 LLM 异步总结历史？ 第一，财税数字差一分钱都不行，LLM 总结很容易把‘增值税草稿待确认 ¥12,400’幻觉成‘已缴款 ¥12,400’；第二，直接投影 Main 数据库里的持久任务台账本身就是 100% 准确的真值，而且耗时仅 3ms、零额外 Token 开销；第三，我们在记忆载荷里强制注入了 authority='context_only_not_approval'，声明记忆仅作上下文参考，绝不替代实时权限校验与用户审批。”

【标准回答话术】：

  • DAG 拆解与细粒度权限（`P-116`）：当用户提出‘先查本月发票再准备增值税申报草稿’时，/a2a/route 将其拆解为有向无环图（TaskGraph）。每个子目标不仅有 dependsOn 依赖列表，还拥有独立的 intent_mode——查发票节点是 business_query（只读），报税节点是 business_prepare（草稿态）。
  • 依赖产物传递（`graphDependencies`）：当上游 Invoice Agent 执行完毕后，TaskGraph 自动解锁下游 Tax Agent，并将上游产出的结构化发票汇总放入 graphDependencies 传给 /plan，让下游规划器直接基于真实查询结果生成算税步骤。
  • 并发槽位与防死循环：每个企业最多允许 2 个并发业务槽位（2-Slot Lease），防止触发税局风控；在单 Agent 内部，我们对每步调用的 tool_name + canonical_args 计算 SHA-256 指纹，一旦连续出现重复调用或连续无状态进展（No-Progress），立即触发中断熔断，绝不死循环空转烧 Token。

【标准回答话术】：

“这是我们在 tools-service 和 main-service 设计中花心思最多的地方，共有 四道防线：
1. 写前意图落盘（Write-Ahead Intent Ledger）：在真正发出 HTTP 写请求之前，必须先以幂等键 operation_id = task_id + step_index + draft_hash 在数据库登记 intent_recorded。
2. 超时锁定为 `outcome_unknown`（严禁自动重发写请求）：一旦写调用发生网络超时或 502/504，任务状态绝对不会回退到 `queued` 自动重跑写接口，而是原子跃迁到 outcome_unknown。
3. 只读对账恢复（Reconciliation Only）：处于 outcome_unknown 的任务在恢复时，只允许调用只读的订单/申报状态查询接口核实上游到底有没有落账；查明已成功则推进为 succeeded，查明未执行才允许安全恢复。
4. `executionVersion` 版本围栏（防僵尸进程迟到回写）：每次派发子进程 Worker 时递增 executionVersion。如果旧 Worker 卡住超时后突然活过来尝试写回结果，main-service 发现它的版本号落后于当前任务版本，会直接以 409 STALE_WORKER 拒绝，彻底杜绝并发状态污染。”

【标准回答话术】：

  • 半开单探测原子租约熔断器（`circuit.py` / `P-081`）：按 domain:upstream 粒度统计故障。当上游连续 3 次超时/5xx 时熔断器打开（open，冷却 60 秒），期间新任务直接安全停靠为 paused(hold) 而不去雪崩式冲击税局。冷却期满进入 half_open 后，通过原子锁只放行唯一 1 个探测请求（附带 120s 探测租约）；探测成功则闭合恢复，探测失败或崩溃则在 finally 中释放租约并重新打开熔断。
  • 根任务 Reserve → Settle 共享预算台账（`WP-03`）：为了防止多 Agent DAG 拆出多个子任务后各自放大消耗，我们将所有子任务收敛到同一个 rootTaskId 共享预算账本（默认上限：32 步工具调用 / 80,000 Tokens / ¥1.50 成本）。每次调用模型或工具前先原子预留（Reserve）额度，调用结束后按真实消耗多退少补结算（Settle）；一旦触及水位线，任务自动转入 paused(reason="budget_hold") 等待人工授权扩容。
