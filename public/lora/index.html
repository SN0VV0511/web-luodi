读完后，你能画出训练和聊天的两条链路，解释 Prompt、RAG、微调各自改了什么，并说清楚项目需要哪些证据。

假设你已经有一个会聊天的基座模型。你希望它像“沐雪”那样回应“今天学习好累”，同时还要认真回答问题。你可以临时告诉它如何说话，也可以给它补充资料，还可以用一批示范对话训练一个小适配器。这三个动作改变的对象不同。你要做的是判断：增加训练这一步，是否带来了值得付出的收益，而不是先认定微调肯定更好。

  1. 01

    先分清两段程序：训练一次，聊天很多次

    训练是拿许多“问题＋理想回答”给模型练习，计算它哪里预测得不准，再更新允许修改的参数。聊天则是把一个新问题交给训练后的模型，让它逐个生成 token，也就是模型处理文字的小单位。一次训练可以服务很多次聊天；用户每发送一条消息，通常不会触发一次训练。先分清这两条链，后面的数据、梯度和部署才不会混在一起。

    对应到实现

    训练：先评分，再找调整方向，最后才改参数

    1. 准备练习题：给出“用户问题＋参考回答”，这是训练数据。
    2. 换成模型能计算的格式：对话模板标出谁在说话，分词器把文字转成 input_ids（输入词元编号）。
    3. 算预测：forward（前向计算）用当前参数计算每个候选词元的分数。
    4. 给预测评分：loss function（损失函数）规定评分规则；loss（损失值）是这次算出的偏差分数。交叉熵损失会惩罚“正确答案概率太低”。
    5. 求该往哪里调：backward（反向传播）从损失出发求梯度，说明每个参数稍作变化会怎样影响损失。此时参数还没更新。
    6. 真正修改参数：optimizer.step（优化器更新）使用梯度和学习率修改允许训练的参数。梯度下降的基本思路是朝梯度反方向移动；LoRA 通常只更新 A、B 等指定参数。

    聊天推理：使用已经学好的参数生成回答

    输入问题 → 相同对话模板与分词 → base（基座模型）＋adapter（适配器）一起计算 → generate（逐词元生成）。通常不记录用于训练的计算图，也不执行 backward 或 optimizer.step。model.eval()（评估行为）与关闭自动求导是两个不同设置。

    沿着这个具体例子想

    训练：给 3375 条对话做若干轮练习。推理：用户输入“今天学习好累”，输出一段回答。这些样本数量来自你的记录，不代表本页执行过真实训练。

    容易误解的地方

    网页中播放训练动画不会改变 Gemma 的权重。真实数值小实验只训练了教学用的小矩阵；它的 loss 不能作为 Gemma 训练效果。

  2. 02

    基座和适配器：原来的能力，加上一份学到的调整

    基座模型就是已经预训练好的模型，它提供语言理解、知识和生成能力。适配器是你额外训练出来的一小份参数，用来调整部分计算结果。可以把它理解为给现有程序加了一条可学习的修正分支：基座仍然工作，修正分支也参与工作，两者合成最终输出。适配器不能独立聊天，必须配合兼容的基座和输入格式。

    对应到实现

    LoRA 常写成 y＝Wx＋(α/r)BAx。base 保存原权重 W，adapter 保存新增的 A、B 及其配置；基础模型版本、目标层和适配器配置必须匹配。

    容易误解的地方

    输出目录存在不等于推理已加载它。没有检查模型和适配器路径，风格没变化时就增加 epoch，可能一直在测试原模型。

  3. 03

    Prompt：这次请求里，直接告诉它怎么回答

    Prompt 就是发给模型的输入说明，例如“你叫沐雪，说话亲切、自然，先回应用户情绪”。它不会修改模型权重，而是影响这一次请求及其上下文中的生成。这样做上手快，适合先验证角色定义是否清楚。如果简单说明已经足够，训练的收益可能很小；如果不同话题下经常偏离风格，才值得进一步做对照实验。

    对应到实现

    system 和 user 消息经过聊天模板转换成模型输入。训练与推理要核对角色说明和模板是否一致；Prompt 的效果应作为 LoRA 实验的基线。

    沿着这个具体例子想

    基线 A：原模型＋“亲切自然”的 system。实验 B：相同原模型＋相同 system＋你的 LoRA。两组问同一句话，才能更直接比较适配器的贡献。

    容易误解的地方

    不能让 A 没有角色提示、B 有详细角色提示，然后把所有风格提升都归因给 LoRA。这样同时改变了两个因素。

  4. 04

    RAG：先查资料，再把资料放进这次请求

    RAG 是“先检索，再生成”：系统先从知识库找到相关资料，再把资料和问题一起交给模型。它主要解决“回答需要什么资料”，资料更新后可以重新检索。微调则通过训练参数影响输出习惯和任务能力。你的目标是说话风格，因此 LoRA 有直接研究价值；如果目标是回答公司最新制度，先做资料检索往往更容易更新和追溯。

    对应到实现

    RAG 修改的是每次请求的上下文，LoRA 修改的是可训练适配器参数。两者可组合；微调也可能学到事实，但不能把它当作可靠、可随时更新的数据库。

    沿着这个具体例子想

    问“本月报销上限”：检索最新制度；问“请用沐雪语气解释制度”：检索提供事实，角色提示或适配器影响表达。

    容易误解的地方

    不要用风格训练数据承诺模型掌握全部专业知识，也不要认为 RAG 自动解决角色稳定性。先把知识正确和表达风格分别评估。

  5. 05

    微调到底想学到什么：回答问题，同时保持风格

    训练集相当于一组示范：遇到这种问题，可以用这种方式回应。模型并不会自动替你区分“值得学习的语气”和“碰巧出现在答案里的错误”。如果示范总是敷衍，它也可能学会敷衍；如果总是插入同一句口头禅，它可能变得机械。因此不能只统计“哦、嘛、啦”出现多少次，还要看答案是否贴题、自然，以及知识能力有没有退步。

    对应到实现

    SFT 即监督微调，用参考回答产生训练信号。它直接优化的是参考 token 的预测损失，风格一致性和任务质量还需要生成评测验证。

    沿着这个具体例子想

    “先休息一下，你已经很努力啦”需要同时满足两点：对“学习累”给出合适回应，表达又符合角色；单独回复“啦啦啦”不能算风格成功。

    容易误解的地方

    训练 loss 下降说明更会预测这份数据，不足以证明更会聊天，更不能证明对新问题都有提升。

  6. 06

    项目闭环：拿什么证明这是你做过的工程

    一个能讲清楚的项目需要把选择、实现和证据连起来：为什么选择 QLoRA，数据怎么处理，哪些参数参与训练，训练是否稳定，加载的是哪个适配器，未见问题上效果怎样。配置文件说明你打算怎么做，日志说明程序实际做了什么，公平对比说明结果是否值得。三类材料对应不同证据，不能用一份 YAML 替代全部结果。

    对应到实现

    保留数据版本与划分、模型和依赖版本、训练配置、checkpoint 路径、资源记录以及固定评测输出。验证集用于选择配置，最终测试集应与调参过程隔离。

    沿着这个具体例子想

    可以展示一张实验表：base＋prompt、base＋prompt＋LoRA；记录同题输出、风格评分、回答质量、峰值显存与耗时。未实测的位置明确写“未测”。

    容易误解的地方

    能导出适配器、能启动本地推理、能提供在线服务，是不同完成阶段。简历只写实际完成且能拿出证据的阶段。

一条公式，两条计算分支。

这条公式描述一个线性层怎样处理一份输入特征：原来的大模型分支先算出一个结果，LoRA 新增的小分支再算出一份修正，两份结果相加。本页统一把向量写成列向量，示例只有 3 个输入数字、2 个输出数字。为了突出 LoRA，公式省略了偏置（bias，线性层额外加上的常数向量）；真实模型还包含许多层、非线性变换和注意力结构。这里算出的 y 是这一层的输出特征，不是整段中文回复，也不是直接输出的下一个字。

下面每一个符号都能点开。先看中文名，再看数字是怎样算出来的。

＝＋
y 等于 W 乘 x，再加上 alpha 除以 r，乘 B，乘 A，乘 x。先计算 A 乘 x，再用 B 映回输出维度，最后乘缩放系数，与 W 乘 x 的结果相加。白话就是：原模型的答案特征，加上一份经过控制大小的可训练修正。

用同一组小数字，六步手算

查看本例所有输入数字和矩阵

x（输入特征），3 行 1 列[1, 2, 3]ᵀ

W（原层权重），2 行 3 列[[1, 0, 2], [0, 1, 0]]

A（降维矩阵），1 行 3 列[[1, 0, -1]]

B（升维矩阵），2 行 1 列[[0.5], [-1]]

α（阿尔法，缩放超参数）＝2；r（秩，中间通道宽度）＝1；因此 α/r＝2。

所有数字都是可手算的教学示例，已用独立 Python 矩阵乘向量计算核对；它们不是 Gemma 实际权重，也不是实测训练效果。A、B 特意取为非零值，用来演示已产生修正后的运算；常见初始化会将 A 随机初始化、B 初始化为零，使初始修正为零。

为什么两条分支可以合并成一张权重？

维度核验：W[2×3]x[3×1] 和 B[2×1]A[1×3]x[3×1] 都得到 [2×1]，因此可以相加。

逐项核验：7 + 2×(-1) = 5；2 + 2×2 = 6。

增量核验：ΔW = (α/r)BA = [[1, 0, -1], [-2, 0, 2]]，其中 Δ 读作德尔塔，表示变化量。

合并核验：W + ΔW = [[2, 0, 1], [-2, 1, 2]]；再乘 x 仍得到 [5, 6]ᵀ。两种写法在这个理想的数值例子里等价。

范围提醒：这个例子只是一个线性层；真实模型一般给多个选定的线性层分别添加各自的 A 和 B。

面试时，怎样用自己的话完整讲这条公式？

可以这样讲：LoRA 冻结原线性层的权重 W，另外训练两个小矩阵 A 和 B。输入 x 一路经过 W，另一路先经过 A 压到 r 维，再经过 B 映回输出维度，乘以 α/r 后与原结果相加。A、B 学习的是新增修正，并不是先把原 W 分解。r 决定瓶颈宽度，使更新矩阵的秩至多为 r；α/r 控制新增分支的尺度，学习率则控制参数更新步长。冻结 W 是不更新它的值，它仍参加前向计算。公式里的 y 只是一个线性层的输出特征，不能直接当成模型的完整回复。

    用一个刻意缩短的例子学习：用户说“累”，助手答“休息吧”。假设模板与分词后得到8个教学token：[BOS, USER, 累, ASSISTANT, 休息, 吧, EOT, PAD]。最后的PAD只为把数组补到长度8，EOT表示助手这一轮结束。这里的名字、编号和分词均是人工示意，不是Gemma的真实模板。下方讲解、交互表和causal_loss_demo.py使用同一个例子。

    1. 01

      分词：先把文字和边界标记变成整数

      神经网络接收数值，不能直接拿Python字符串做矩阵乘法。分词器先把内容拆成token，再按词表换成编号；聊天模板还加入角色和结束边界。本例人为令BOS＝1、USER＝11、累＝12、ASSISTANT＝2、休息＝21、吧＝22、EOT＝3、PAD＝0。“休息”在这里是一整个token，最后补一个PAD，把数组对齐到8个位置。

      对应到实现

      input_ids＝[1,11,12,2,21,22,3,0]。真实项目必须使用匹配模型的tokenizer和chat template，不能直接使用这些教学ID。

      沿着这个具体例子想

      位置0→BOS(1)，1→USER(11)，2→累(12)，3→ASSISTANT(2)，4→休息(21)，5→吧(22)，6→EOT(3)，7→PAD(0)。EOT结束助手轮次，PAD只是补齐位置。

      容易误解的地方

      一个汉字不一定是一个token，一个词也可能被拆开。本例把“休息”当一个token是教学约定；真实长度必须以真实分词结果为准。

    2. 02

      张量：给数组增加批次，再变成每个token的特征

      张量可以先理解为有形状的多维数组。一次送入1条、补齐后8个位置，输入形状就是[1,8]。模型按编号查表，把每个token换成一排浮点特征。假设特征宽度是6，就得到[1,8,6]。这里的6不是字数，而是每个位置使用多少个特征数表达。PAD也有一个位置，但它不是需要学习生成的正文，后面要正确屏蔽。

      对应到实现

      B＝batch size，T＝sequence length，H＝hidden size。Embedding把[B,T]的整数索引映射为[B,T,H]的浮点特征；attention_mask标明哪些位置是真实输入。

      沿着这个具体例子想

      B＝1、T＝8、H＝6：输入有8个整数；嵌入后有8排特征、每排6个数。attention_mask＝[1,1,1,1,1,1,1,0]，最后一格标明PAD。

      容易误解的地方

      input_ids是整数索引，hidden states是浮点特征。不要把PAD编号0和attention_mask里的0混为同一个字段：前者是token ID，后者表示屏蔽位置。

    3. 03

      logits：每个位置给32个候选token打分

      模型在每个位置都输出一排候选分数，这排原始分数叫logits。本例词表有32个token，所以输出形状是[1,8,32]。Softmax把每排分数转成总和为1的概率。若所有分数一样，每个候选都得到1/32的概率；模型还没偏向任何答案。训练会检查正确token分到多少概率，而不是只看最高分是否碰巧选对。

      对应到实现

      logits[b,t,:]表示读完位置t及以前内容后，对下一个token的词表分数。交叉熵可直接接收logits，在内部做数值稳定的log-softmax；均匀预测的CE是ln(32)≈3.46573590。

      沿着这个具体例子想

      读完位置3的ASSISTANT后，若模型给“休息”0.60，其他31个候选合计0.40，则这一题按正确token“休息”的0.60概率计分；真实参考ID是21。

      容易误解的地方

      logits不是百分比。CrossEntropyLoss通常要求原始logits，不要先softmax后再把概率传进去；也不要把这里的32当成Gemma真实词表大小。

    4. 04

      labels：Prompt不计分，PAD也不计分

      我们保留整条输入，通常只给助手回答及其结束标记评分。labels相当于“评分答案表”：前4个Prompt位置填-100，回答“休息”“吧”和EOT保留原ID，最后的PAD也填-100。-100不是让模型生成的词，而是约定“这格不计分”。因此一共只有3个有效答案。用户说的“累”仍在输入里，会影响模型如何回应。

      对应到实现

      labels＝[-100,-100,-100,-100,21,22,3,-100]；attention_mask＝[1,1,1,1,1,1,1,0]。前者控制监督损失，后者标记有效输入；因果遮罩另行控制不能看未来。

      沿着这个具体例子想

      位置0 BOS→忽略；1 USER→忽略；2 累→忽略；3 ASSISTANT→忽略；4 休息→计分；5 吧→计分；6 EOT→计分；7 PAD→忽略。

      容易误解的地方

      三种mask不要混淆：labels的-100决定是否计入loss，padding mask屏蔽补齐位置，causal mask阻止偷看未来。设置attention_mask不等于自动把所有PAD标签排除，labels也要核对。

    5. 05

      shift：位置3的输出，负责预测位置4的“休息”

      自回归的规则是“根据前面预测后面”。位置3读到ASSISTANT后，应预测位置4的“休息”，不能拿它与位置3自己比较。把logits去掉最后一格，把labels去掉第一格，两边就对齐了。有效题只有3道：ASSISTANT后预测休息，休息后预测吧，吧后预测EOT。位置6后面的PAD标签被忽略，位置7输出则没有下一个参考位置。

      对应到实现

      shift_logits＝logits[:,:-1,:]，shift_labels＝labels[:,1:]，再用ignore_index＝-100计算交叉熵。许多CausalLM的forward(labels=labels)已经内部shift，外部不要再移一次。

      沿着这个具体例子想

      7个对齐项：logits[0]→labels[1]忽略；[1]→[2]忽略；[2]→[3]忽略；[3]→[4]休息21；[4]→[5]吧22；[5]→[6]EOT3；[6]→[7]PAD忽略。

      容易误解的地方

      用位置4的输出预测位置4的“休息”，模型已经看到答案，会错置目标。不要因为最后有PAD，就把前面的EOT也一起删除：本例EOT是需要学习的结束信号。

    6. 06

      交叉熵：只把3道有效题的扣分取平均

      交叉熵可理解为“正确答案概率越小，扣分越多”。若3道题分别给正确答案0.6、0.5、0.8的概率，每题取负对数，再除以3，平均loss约0.47570545。反向传播计算参数怎样影响这个误差，优化器再更新。若32个候选等概率，平均loss是ln32，约3.46573590。两组数都只是教学示意，不能当Gemma训练指标。

      对应到实现

      L＝[-ln(0.6)-ln(0.5)-ln(0.8)]/3≈0.47570545；均匀logits的L＝ln(32)。backward求梯度，step更新参数；训练使用真实前缀的方式称teacher forcing。

      沿着这个具体例子想

      有效监督数是3，分母不是8，也不是shift后的7。代码中uniform logits输出ln32可校验损失实现；正确概率示例用于说明概率越高、CE越低。

      容易误解的地方

      训练时预测“吧”能看到参考前缀“休息”，聊天时则依赖自己生成的前缀，所以低loss不等于自由生成一定好。无有效label的样本也需要提前排查。

      先说明原因，再进入代码 / CHAPTER 03

      你能从输入维度推导 A、B 的形状，算出参数量，解释低秩、初始化、冻结和梯度为何这样设计。

      把一个线性层看成“把输入的一排特征混合成输出的一排特征”。原矩阵 W 已经学到了有用的转换，LoRA 不直接改它，而是额外训练一个先降到 r 维、再升回输出维的修正分支。理解维度后，公式不再是一串字母；理解初始化和梯度后，你就能回答代码里为什么某个参数第一步看起来没有动。

      1. 01

        先读矩阵乘法：每个输出都是输入的加权组合

        先用一个小层举例：输入有3个特征，输出有2个特征，那么 W 可以写成2行3列。每一行拿3个权重分别乘3个输入，再相加，得到一个输出。于是3个输入变成2个输出。对一批数据，代码往往把样本放在行上，写成 x 乘 W 的转置。写法不同，表达的是同一个线性变换；先标清输入、输出轴，就不会把 A、B 放反。

        对应到实现

        采用列向量公式时 x∈R^in、W∈R^(out×in)、y＝Wx∈R^out。PyTorch F.linear 的批量写法为 x[B,in] @ W.T[in,out]，输出[B,out]。

        沿着这个具体例子想

        x＝[1,2,3]；W第一行为[1,0,2]，第一输出为1×1＋0×2＋2×3＝7。第二行若为[0,1,0]，第二输出就是2。

        容易误解的地方

        不要只记“先乘 A 再乘 B”，却忘记库中的权重布局。这里使用 A[r,in]、B[out,r]；别的资料可能采用转置命名。

      2. 02

        原支路给基础结果，小支路给修正量

        LoRA 把输出分成两部分：W 算出原来的结果，A、B 算出需要补上的变化。A 先把输入压到 r 个中间特征，B 再把它展开回输出宽度，两路结果相加。这里压缩的是“新增调整分支的通道数”，不是把原来的 W 丢掉。训练后 W 仍是原值，变化储存在 A、B 中；推理时这个变化会真正影响层输出。

        对应到实现

        A∈R^(r×in)、B∈R^(out×r)，所以 BA∈R^(out×in)，与 W 同形状。标准 LoRA 为 y＝Wx＋sBAx，s＝α/r；实际代码可用两次 F.linear 顺序实现。

        → 看每个字母的中文解释，并用六步手算得到 y=[5,6]
        沿着这个具体例子想

        in＝3、out＝2、r＝1：A把3维输入变成1个数，B把这个数变成2维修正，最后与原2维输出相加。两路都产出2维，所以能相加。

        容易误解的地方

        LoRA 不是先对预训练 W 做一次 SVD 分解，再拿两个小矩阵替代它。常规 LoRA 是学习新增的 ΔW＝sBA。

      3. 03

        低秩为什么省：少数调整方向，不存一个完整增量矩阵

        如果原层是2048输入、2048输出，完整修改矩阵有4194304个参数。r＝8时，A是8×2048，B是2048×8，总共32768个参数，只是这个原矩阵的1/128。直观上，新增变化要通过8个中间通道表达，因此自由度受到限制。这种限制常常足以完成某些任务，但并不保证任何任务都够用，需要用实验检查。

        对应到实现

        完整矩阵参数为 in×out；LoRA 参数为 r×in＋out×r。rank(BA)≤r，因此称为低秩更新；多层模型总比例还取决于插入位置、各层形状和额外可训练模块。

        沿着这个具体例子想

        2048²＝4,194,304；8×2048＋2048×8＝32,768。只计算这一层的参数量：32768/4194304＝0.78125%。

        容易误解的地方

        单层少128倍参数，不等于整模型显存少128倍。冻结基座仍要加载，激活值和临时工作区也仍存在。

      4. 04

        为什么 A 随机、B 为零：开始时先不扰动原模型

        常见初始化让 A 是小的随机数，B 全为零。因为 B 为零，BA 也为零，新分支一开始加上的是零，模型输出等于原模型。第一次反向时，B 能得到梯度，因为它前面已经有 A 产生的信号；A 的任务梯度则要经过 B，B 为零会把这条梯度挡成零。B 更新后，后续步骤中 A 也通常能获得非零梯度。

        对应到实现

        设上游梯度为g，∂L/∂B＝s·g·(Ax)^T；∂L/∂A＝s·(B^Tg)·x^T。B＝0时后式为0；前式可能非零，但也取决于输入和损失梯度。

        沿着这个具体例子想

        第一轮 backward：A.grad可能恰为0，B.grad非零；step 后 B不再全零。第二轮再看 A.grad，通常就能看到学习信号。

        容易误解的地方

        不能说“A第一步绝不会变化”：AdamW权重衰减等非任务梯度因素可能改变参数。严谨说法是零B初始化时A的首步任务梯度为零。若A、B都为零，两者的任务梯度都会受阻。

      5. 05

        冻结 W：不更新它，但不能跳过它的计算

        冻结指的是不为 W 累积并应用参数梯度，不是关掉这条支路。前向仍要计算 Wx，因为它提供模型的基础输出。反向也要沿模型的计算关系把误差信号传到各个 LoRA 层，否则前面的小分支无法学习。你可以检查 W 的 requires_grad 为假、没有参数梯度，同时确认 A、B 被放进优化器；这比只相信“已冻结”的打印信息更可靠。

        对应到实现

        W.requires_grad_(False) 禁止更新W；优化器通常只接收requires_grad=True的参数。冻结权重的运算仍可能需要对其输入求导，所以不能把整个基座前向包进 no_grad 后期待多层 LoRA 正常训练。

        沿着这个具体例子想

        在教学实验中保存 W_before，更新后与 W_after 比较应相等；再检查 B或后续A是否变化，以及 loss 是否按预期计算。

        容易误解的地方

        所有 .grad 都为 None 不代表“省显存成功”，也可能是误用了 no_grad、没有有效 labels，或优化器没有包含适配器参数。

      6. 06

        α、rank 和合并：分清容量、缩放与产物形态

        rank 控制新增分支能容纳多少调整方向，alpha 参与控制分支输出尺度；标准设置 r＝8、alpha＝16 时比例为2。它不等于把优化器学习率直接乘2，因为参数、梯度和更新会相互作用。训练后可以继续用两条分支，也可以把 sBA 加到 W 中合并成一个矩阵。合并前后在相同精度下应近似一致，但有限精度和量化可能带来误差。

        对应到实现

        标准缩放s＝α/r；其他变体可能用不同缩放，需看配置。eval 模式关闭LoRA dropout后，W_merged＝W＋sBA；合并产物需核验精度和推理结果。

        容易误解的地方

        rank更大不一定更好，alpha更大不一定收敛更快。比较rank时需控制训练条件并记录资源和效果，不能靠公式直接断言最优。

        4-bit 是存储策略，
        不是全程计算精度。
        “模型4-bit加载”和“整场训练都用4-bit”是两件事。先把显存分账，再分别看权重如何存、运算用什么精度、适配器和优化器保存什么。
        

        01 先读白话02 看动画03 逐段读代码04 查术语05 面试复述
        先说明原因，再进入代码 / CHAPTER 04
        你能解释LoRA与QLoRA的区别，按类别分析OOM，读懂NF4、双重量化与BF16，而不背一个未经实测的显存数字。
        把显存看成同一间工作室：基座权重是常驻设备，适配器是可调工具，激活值是每批处理中间稿，梯度和优化器状态是修改记录，临时工作区是运算时占用的桌面。QLoRA主要缩小常驻设备的部分存储，不会让其他物品消失。因此同一个模型，序列长度、批量、目标层和评估方式不同，峰值也会不同。
        1. 01
          先列完整账单：参数不是训练时唯一的大项
          加载模型后，显存里不只有权重。训练还要保存部分中间结果，反向时使用；可训练参数有梯度，优化器还可能保存历史统计；某些算子会临时申请工作区。于是“模型文件有几GB”不能直接推出“训练需要几GB”。真实峰值还可能出现在评估、生成或保存阶段。遇到OOM，先判断哪一步、哪类分配增长，处理才有针对性。
          对应到实现
          常见账本为：基座权重＋适配器参数＋梯度＋优化器状态＋激活值＋临时工作区，另有缓存与分配器开销。CUDA allocated 与 reserved 含义不同，也不应与整卡进程占用混为一谈。
          沿着这个具体例子想
          模型加载成功，长样本backward才OOM：应优先检查激活和工作区；如果模型加载阶段已OOM，梯度累积通常帮不上忙，因为尚未处理训练批次。
          容易误解的地方
          不要用模型文件大小、4-bit理论字节数，或任务管理器某一瞬间读数，冒充完整训练峰值。
        2. 02
          LoRA省训练状态，QLoRA再省部分基座存储
          普通LoRA冻结原模型，只训练小适配器，因此大量原参数不需要保存用于更新的梯度和优化器状态。QLoRA在此基础上，进一步把支持的冻结权重用低比特格式保存。两者同时使用时，原模型仍然提供基础计算，适配器仍然以可训练的浮点参数存在。哪些模块真正量化、哪些保留较高精度，要从实际加载结果核对。
          对应到实现
          LoRA约束可训练参数；QLoRA结合低比特冻结基座与LoRA训练。常见bitsandbytes集成主要替换支持的线性层，嵌入、归一化或特定模块不保证都以4-bit存储。
          沿着这个具体例子想
          一项配置写load_in_4bit=True，只说明请求量化加载。还需要查看模块类型、可训练参数、dtype和显存记录，才能知道实际资源结构。
          容易误解的地方
          不能把模型总参数统一乘0.5字节，得到所谓“精确训练显存”；量化元数据、未量化模块和训练额外开销都被漏掉了。
        3. 03
          4-bit存储：先用小编号保存，计算时再恢复近似值
          一个4-bit编号只有16种可能，所以无法逐个精确保存原来的浮点权重。量化会用一套表示规则和比例信息，把很多原始权重映射到有限的编号；需要运算时，再重建它们的近似数值。这样存储更紧凑，但有量化误差，也有比例等额外信息。计算内核可能融合重建与矩阵乘法，不一定把整个完整精度矩阵长期展开在显存里。
          对应到实现
          4-bit描述支持权重的压缩存储；实际乘法通常使用指定计算dtype及相应内核。不要把概念上的dequantization理解成每次必然额外常驻一份完整FP32模型。
          沿着这个具体例子想
          把0.137映射成某个4-bit编号，结合该组比例，使用时近似还原成0.14。这里只为解释有损近似，实际NF4映射不是简单四舍五入。
          容易误解的地方
          “4-bit模型”不表示输入特征、loss、梯度、优化器状态、所有层和所有算子都变成4-bit。
        4. 04
          NF4与双重量化：编号规则和比例信息也要算成本
          NF4可以理解为一种专门设计的16档数值表示：档位不是等间隔，而是考虑某类权重分布，把有限档位分配到更合适的位置。分组量化还需要保存比例等信息，这些信息本身也占空间。双重量化进一步压缩部分量化常量，减少这笔额外成本。它不是让同一权重从4-bit再砍成2-bit，也不是承诺任何模型都完全无损。
          对应到实现
          NF4是面向近似正态权重分布设计的4-bit数值类型。double quantization对部分量化常量再次量化；在bitsandbytes配置里通常对应bnb_4bit_quant_type和bnb_4bit_use_double_quant。
          沿着这个具体例子想
          主账：大量权重用小编号；附账：每组要有比例信息。双重量化压缩附账的一部分，不会取消主账，也不会取消解码所需的全部元数据。
          容易误解的地方
          NF4不等于INT4均匀整数网格。开启双重量化也不代表同时启用了分页优化器、梯度检查点等其他节省手段。
        5. 05
          BF16：计算精度、参数精度、优化器精度分别问

          对应到实现
          分别核对bnb_4bit_compute_dtype、可训练parameter.dtype、梯度dtype与optimizer state。混合精度autocast主要选择算子的计算方式，不等于把所有参数、状态永久改成同一种dtype。
          沿着这个具体例子想
          一种可能组合：部分基座4-bit存储，矩阵运算配置BF16，LoRA参数FP32，Adam统计FP32。具体组合要看框架实现与实际对象，不能仅凭本例断言。
          容易误解的地方
          BF16相对FP16并不会因为位数更少而省一半显存，两者都为16位。BF16也不能自动修复所有NaN、数据错误和训练不稳定。

            1. 01
              先分容量和步幅：rank 不是学习率，alpha 也不是开关
              rank 决定 LoRA 小分支能容纳多少调整方向，像给模型多少张可写的便签；学习率决定每次根据梯度把便签内容改多大。alpha 则控制便签分支加回原答案时的尺度。它们都会影响结果，但位置不同：增加便签张数，不等于写得更猛；把分支贡献放大，也不等于换一个更大的模型。
              对应到实现
              标准 LoRA 的缩放为 alpha/r；r=8、alpha=16 时是 2。learning_rate=5e-5 进入优化器，决定梯度更新的基础步幅。dropout=0.05 在 LoRA 分支训练时施加随机失活，推理时关闭；具体作用位置按实现核查。
              沿着这个具体例子想
              固定 alpha/r=2，比较 r=4、8、16，能减少缩放比例变化的干扰，但参数容量、优化轨迹依然不同。没跑对照实验前，只能称 r=8 为起始配置。
              容易误解的地方
              alpha/r=2 不代表“等价于学习率翻倍”。前向结果、梯度、优化器状态和非线性网络共同决定实际更新。
            2. 02
              用 8 条作业看梯度累积：先记账，最后一起更新
              单卡 batch=1 时，显卡一次只处理 1 条样本。第 1 条算完梯度先留下，第 2 条把梯度加上去，依次到第 8 条，再执行一次参数更新并清空梯度。因此前 8 条通常使用同一份参数，只是梯度逐渐积累。这样不用同时保存 8 条的激活，也能形成约 8 条样本一次的更新节奏。
              对应到实现
              一个微批次通常执行 forward、loss.backward；满足梯度累积边界后才执行 optimizer.step、scheduler.step 和 zero_grad。单卡、无其他批量语义变化时，有效样本批量约为 micro_batch × accumulation × world_size=1×8×1=8。
              沿着这个具体例子想
              第 1～7 条：参数版本仍是 v0，梯度逐步累积。第 8 条结束：用累积梯度得到 v1。第 9 条才使用 v1。动画里的“样本数”和“更新数”因此不能同步加一。
              容易误解的地方
              别每看一条就 optimizer.step 再声称累积了 8 次。也别清空得太早，否则前面留下的梯度会丢失。
            3. 03
              尾批与长短答案：8 条样本不等于固定数量的训练 token
              如果一轮有 10 条样本，前 8 条能完整累积，最后只剩 2 条。训练器通常会在轮末处理这份尾批，但是否保留、怎样缩放要看实现。另外，一个回答只有 5 个 token，另一个有 50 个：先对每条取平均再平均，和把 55 个 token 放在一起平均，给两条回答的权重不同。这正是“近似大批量”需要核查的地方。
              对应到实现
              尾批涉及 dataloader_drop_last 与梯度累积的 remainder 处理。监督 token 数为 count(labels != -100)，不是整段输入长度。等权平均微批 loss 与按有效 token 加权的全局平均可能不同；手写循环不能一律把最后 2 条也除以 8。
              沿着这个具体例子想
              短答案 loss=1、5 个监督 token；长答案 loss=3、50 个监督 token。按样本均值是 (1+3)/2=2；按 token 均值是 (5×1+50×3)/55≈2.82。两者都是明确目标，但不是同一个目标。
              容易误解的地方
              不能把有效 batch=8 理解为严格等同于任何实现的一次 batch=8；损失归一化、随机失活、尾批处理等都可能产生差异。
            4. 04
              epoch、step 和学习率调度：遍历几遍，更新几次，步幅怎么变化
              epoch 是整份练习册大致看一遍，step 在常见日志里指真正更新一次参数。3375 条、每次约 8 条形成更新，一轮约 422 次，三轮约 1260 多次。warmup 让开始阶段先小步适应，之后 cosine 逐渐减小步幅。它们是在安排同一个学习过程的节奏，不会自动保证收敛，更不会自动找到最佳轮数。
              对应到实现
              num_train_epochs=3 控制遍历次数；global_step 通常按 optimizer update 计数。warmup_ratio=0.1 按计划总更新步数计算预热区间；lr_scheduler_type=cosine 决定后续变化。精确步数受尾批、打包、分布式与框架版本影响，以日志为准。
              沿着这个具体例子想
              假设最终计划 1266 次更新，10% 预热约为前 127 次；logging_steps=10 约为每 10 次参数更新记日志，不是每 10 条样本记一次。这里的 1266 是示意估算。
              容易误解的地方
              看到“三轮”就说不会过拟合，或者看到 loss 仍下降就无限加轮数，都缺少验证集与新题输出证据。
            5. 05
              保存与恢复：能继续推理，不等于能接着同一条训练轨迹跑
              只保存 LoRA 权重，通常足以让基座加上它继续回答；但要中断后接着训练，还需要知道优化器记住的动量、学习率走到哪一步、当前进度与随机状态。缺少这些信息，再加载权重开练更像“从这份参数重新开一轮训练”。两种行为都可能有用，但面试时要把它们区分清楚。
              对应到实现
              save_steps 常按更新步保存。完整可恢复 checkpoint 可能包含 adapter、optimizer、scheduler、trainer_state 与 RNG 状态；save_only_model 等选项会影响内容。resume_from_checkpoint 应指向完整检查点，并核验配置、数据顺序和软件兼容性。
              沿着这个具体例子想
              第 400 步断电。恢复 adapter 可找回第 400 步参数；若学习率调度器被重置，下一步的步幅可能又回到预热阶段，因此不是原来的第 401 步训练状态。
              容易误解的地方
              “固定随机种子”也不保证跨 GPU、驱动或框架版本逐位复现。恢复日志应明确加载了哪些状态，而不是只看文件夹名字。

              一个学生把练习册背熟，练习分数会越来越高。但面试官更关心换一道题还会不会做。loss 像练习表现，对照评测像换题考试；两种证据放在一起才完整。
              1. 01
                loss 是怎么来的：正确答案越不被看好，惩罚越大
                假设标准答案下一个 token 是“休息”。模型给它 50% 概率，说明它还算看好；只给 10%，说明它更倾向别的写法。训练会对后一种情况罚得更重，并把梯度传回 LoRA 参数。每个需要评分的 token 都这样算，再按约定平均，得到日志中的 loss。所以 loss 不是“答错了几个字”，而是对正确 token 的概率评价。
                对应到实现
                常见因果语言模型 SFT 使用交叉熵：单个目标 token 的损失为 -ln p(correct token)。只对 labels 未屏蔽的位置汇总。p=0.5 时约 0.693，p=0.1 时约 2.303；概率来自词表上的 softmax，logits 本身不是概率。
                沿着这个具体例子想
                教学中只有两个受监督 token，它们正确答案的概率是 0.5 和 0.25：平均 loss=(-ln0.5-ln0.25)/2≈1.040。真实训练会对大量 token 按框架的归一化规则统计。
                容易误解的地方
                下一个 token 有很多合理写法，标准答案只选其中一种；因此更低的文本交叉熵，不总能直接对应更自然或更有用的回答。
              2. 02
                PPL 是 loss 的另一种表达，不是另一次人工打分
                为了把平均对数惩罚换成更直观的尺度，经常对 loss 取指数得到困惑度 PPL。可以粗略理解为模型面对正确答案时的平均不确定程度，越低通常越容易预测。它不是“每句话有几个错误”，也不是角色像不像的分数。不同分词器、不同监督位置或不同数据集算出来的 PPL，不能直接拿来排名。
                对应到实现
                在使用自然对数、相同 token 级平均交叉熵口径下，PPL=exp(loss)。上一例 loss≈1.040，则 PPL≈2.83；如果 loss=2，则 PPL≈7.39。必须确认日志的聚合口径与监督范围，不能对任意命名为 loss 的指标都套这个公式。
                沿着这个具体例子想
                网页前面的 NumPy 小实验使用均方误差，目的是演示参数更新，不能把它的 loss 取指数后当成语言模型困惑度。这是两种不同任务的损失。
                容易误解的地方
                不能说“我的 loss 从 2 降到 1，所以角色质量提升 50%”。loss 的变化没有这样的百分比质量含义。
              3. 03
                怎么看过拟合：不能只盯一次验证曲线抖动
                如果训练集越来越好，验证集在多个检查点持续变差，而且新题开始复读或答非所问，就有理由怀疑模型过度适应训练内容。单次验证 loss 上升可能只是波动；训练与验证 loss 的绝对高低，也受数据难度影响。你需要固定同一批验证数据、同一套预处理，结合多次趋势和生成样例判断，再选择较早的 checkpoint。
                对应到实现
                过拟合证据应组合 train/eval loss 趋势、独立生成评测与重复率等观察。模型选择使用验证集，最终测试集只用于最终报告。候选措施包括减少训练时长、调整学习率、正则化与容量，优先单变量对照，避免同时改多项。
                沿着这个具体例子想
                假设第 200、400、600 步验证 loss 为 1.6、1.5、1.7，单看最后一次还不够。若后面持续 1.9、2.1，且新题复读明显增加，早期模型就更值得保留。数字仅为示意。
                容易误解的地方
                不能用训练集里出现过的提问证明泛化；也不能先看测试结果再不断调参数，最后仍把它称为独立测试。
              4. 04
                公平对照：先让角色提示词基线认真参赛
                你要证明的是 LoRA 带来了额外价值，所以两边都应该得到相同角色提示词、相同问题和相同生成设置。一边只有普通模型，另一边同时加入提示词和 LoRA，就分不清谁带来改善。评测还要换训练中没出现的问题，包括多轮和角色不熟悉的话题，看看风格能不能迁移，而不是只背出了几句训练答案。
                对应到实现
                核心对照是“基座＋角色 prompt”对“同一基座＋同一 prompt＋LoRA”。尽量固定基座 revision、tokenizer、模板、量化、temperature、top_p、max_new_tokens。需要稳定比较时固定生成种子或使用确定性解码，并承认运行环境的复现边界。
                沿着这个具体例子想

                容易误解的地方

              5. 05
                指标要能复查：把“感觉更像”变成带样本的观察

                对应到实现
                可记录盲评风格分、回答质量分、A/B 偏好含平局、多轮一致性和重复情况。明确题目数量、评分尺度、评委人数及聚合方式；题目是主要统计单元，多轮同题不是完全独立样本。自动裁判也需固定规则并抽查，不能当作绝对真值。
                沿着这个具体例子想
                报告模板可以是“在 N 道固定新题、K 位评分者的盲评中，A 胜 x、B 胜 y、平局 z”。N、K、x、y、z 必须来自真实实验，本页不会填造提升百分比。
                容易误解的地方
                只展示最好看的三条回答是挑选样例，不是完整评估。简历里的准确率、胜率、显存和耗时必须能追溯到日志与原始输出。
              6. 06
                OOM 按阶段排查：先问显存在哪一步不够
                加载时就爆显存，说明还没开始学习，先看基座权重、量化和多余模型副本；前向或反向爆掉，更该看批量、序列长度、激活和检查点；评估才爆，可能是缓存全部预测或生成太长；导出才爆，要看合并时的精度和临时副本。先记录发生阶段，再动对应旋钮，比碰到 OOM 就盲目降低学习率有效得多。
                对应到实现
                记录 traceback、当前阶段、allocated/reserved 与峰值。加载：检查 device map 与量化；前向：检查 batch/长度/模块；反向：检查 activation checkpointing 与 trainable 参数；评估：检查预测缓存、eval batch 与生成长度；导出：考虑 CPU 内存、精度与完整权重临时副本。
                沿着这个具体例子想
                模型已成功完成 100 步，到了第一次 eval 才 OOM，优先减少评估缓存或 eval batch，而不是立刻把训练 rank 减半。empty_cache 也不能释放仍被活跃 tensor 引用的显存。

                3. 03
                  合并是什么：把小分支加进权重，但精度与成本会变化
                  直接加载时，原权重分支与 LoRA 分支一起参与计算；合并时，把学到的增量加到对应权重里，生成一份合并模型。理想数学下二者可等价，但有限精度、量化和实际实现会产生差异，因此要重新做固定题回归。训练时基座按 4-bit 加载，不代表合并文件还是 4-bit，更不代表导出过程只需要训练时那么多内存。
                  对应到实现
                  标准 LoRA 对线性权重合并为 W'=W+(alpha/r)BA，注意具体层的转置约定。merge_and_unload 等操作是否支持、如何处理量化依赖当前实现。常用导出流程加载未量化基座后合并，再按部署需要量化；完整权重与临时副本会增加内存需求。
                  沿着这个具体例子想
                  教学 NumPy 实验可检验 xWᵀ+s(xAᵀ)Bᵀ 与 x(W+sBA)ᵀ 在浮点误差内一致；真实语言模型还需比较输出、延迟、内存和量化后质量。
                  容易误解的地方
                  支持 LoRA 的推理框架可以直接加载 adapter，不一定必须合并。合并只是产物形式变化；把文件保存出来还不是部署。
                4. 04
                  AI 应用接入：把模型推理放在清晰的服务边界里
                  对 AI 应用工程师来说，下一步是让应用通过明确接口请求生成：输入对话和生成参数，输出文本、结束原因与必要用量。应用要限制输入长度，处理取消和超时；流式接口需要在用户断开后停止不必要生成。风格 LoRA 只改变输出倾向，业务鉴权、工具权限与重要数据校验仍由应用负责，不能交给角色人设决定。
                  对应到实现
                  服务契约至少明确模型版本、messages、max_new_tokens、stream 与错误语义；生成服务配置队列、超时、取消传播、健康检查和最小脱敏观测。保持结构化工具调用与业务授权边界，新增风格模型应做接口与内容回归。
                  沿着这个具体例子想
                  聊天页面发 messages，后端检查用户权限与长度，再调用固定模型版本；若请求超时，返回可识别错误，而不是把半段输出误标为成功。这里是工程设计，不表示本项目已经部署了该服务。
                  容易误解的地方

                5. 05
                  并发与回滚：不是单人能聊，就能稳定服务多人
                  单条请求运行正常，多人同时请求仍可能把显存挤满，因为每段输入和生成都要保存各自的上下文状态。可以限制同时生成数量、控制输入输出长度，并把超额请求排队或明确拒绝。上线新 adapter 时保留旧版，用小范围流量检查质量与性能；出问题能切回旧版，远比临时再训练一个模型可靠。
                  对应到实现

                  沿着这个具体例子想
                  只允许 1 个活动生成并设置有限队列，是小显卡上可解释的起点。它是否满足业务取决于实测延迟；不能仅凭“模型能加载”就承诺每秒处理多少请求。

                  ① 先算工作量：本地模型每秒要处理多少？
                  
    
                  平常日本地请求数 = 税号数 × 日活比例 × 每个活跃税号每天对话轮数 × 本地承接比例
                 = 5,000 × 40% × 8 × 60% = 9,600 次/天
峰值请求率 λ  = 日请求 × 征期倍数 × 峰值小时占比 ÷ 3600 = 9,600 × 2.5 × 15% ÷ 3600 ≈ 1.0 次/秒
需要的输出速度 = λ × 平均输出长度 = 1.0 × 250 ≈ 250 token/s（预填充 1.0 × 1,200 = 1,200 token/s，算力上很轻）
同时在途路数 C = λ × (首字延迟 + 输出长度 ÷ 单路速度) = 1.0 × (0.5 + 250 ÷ 20) ≈ 13 路      ← Little 定律
                  
    
                  这些假设和 1F Biglink 页的容量估算器完全一致。“每路 20 token/s”是体验目标：大约等于每秒 10~15 个汉字，比人的阅读速度快。
                  

    
                  ② 再算显存：权重 + KV 缓存 + 运行开销
                  
    
                  
      
                  权重 = 参数量 × 每参数字节
  Gemma-2-9B（9.24B）：BF16 ≈ 18.5 GB；FP8/INT8 ≈ 9.2 GB；INT4(AWQ/GPTQ) ≈ 5.2 GB

KV 缓存/每 token = 2(K 和 V) × 层数 × KV 头数 × 每头维度 × 字节
  Gemma-2-9B：2 × 42 × 8 × 256 × 2B = 344,064 B ≈ 0.33 MB
  Qwen2.5-7B：2 × 28 × 4 × 128 × 2B =  57,344 B ≈ 0.055 MB

KV 总量 = 在途路数 × 每路上下文长度 × 每 token KV
  Gemma-2-9B：13 × (1,200+250) × 0.33 MB ≈ 6.5 GB

运行开销 ≈ 2.5 GB（CUDA 上下文、激活、CUDA Graph 等，经验值）
可用显存 = 显存 × 0.9（vLLM 的 gpu_memory_utilization）
                  
      
                  为什么 KV 缓存这么重要？生成每个新 token 时，模型要回看之前所有 token 的 K、V 向量，这些向量缓存在显存里，按“路数 × 上下文长度”增长。权重是固定成本，KV 是随并发增长的成本，决定了一张卡能同时服务多少人。
                  模型结构差异很大：Gemma-2-9B 的每头维度是 256、有 42 层，每 token 的 KV 是 Qwen2.5-7B 的 6 倍。所以“参数量差不多”不代表“能扛的并发差不多”，选基座时要看 config 里的 num_hidden_layers / num_key_value_heads / head_dim。
                  注：Gemma-2 有一半层用 4K 滑动窗口，上下文不超过 4K 时省不了 KV，这里按全量算，偏保守。
                  
    
                  

    
                  ③ 最后算速度：一张卡每秒能生成多少 token？
                  
    
                  
      
                  解码阶段是“搬显存”受限：每生成一步，要把全部权重 + 所有在途路的 KV 读一遍
每步读取量 = 权重 + C × 平均上下文 × 每 token KV
单路速度 ≈ 显存带宽 × 有效系数 ÷ 每步读取量        （token/s）
整卡吞吐 ≈ 单路速度 × C

例：L20（864 GB/s），Gemma-2-9B FP8，C=13，平均上下文 1,325
  每步读取 ≈ 9.2 + 13 × 1,325 × 0.33MB ≈ 15.2 GB
  单路 ≈ 864 × 0.7 ÷ 15.2 ≈ 40 token/s  → 整卡 ≈ 520 token/s ≥ 需要的 250 ✓
                  
      
                  有效系数 0.7 怎么来的？用公开基准反推：一篇在 L40S（同为 864 GB/s）上用 vLLM 跑 Llama-3.1-8B 的实测，BF16、16 路并发的聊天负载约 633 token/s；代入上面的公式，有效带宽约为标称的 80%。这里取 70%，偏保守。
                  vLLM 的连续批处理（continuous batching）是关键：同一篇实测里，并发从 1 提到 256，吞吐从 47 提到 3,415 token/s。所以单路慢 ≠ 整卡慢，要看并发下的总吞吐。
                  来源：vLLM optimization playbook for L40S（83 组实验）；Red Hat MLPerf v5.1：L40S 跑 Llama-3.1-8B FP8 约 1,207 token/s（Server）。不同模型、负载差异很大，上线前必须用自己的 prompt 分布压测。

                  方案 A：合并权重（推荐起步）
                  训练完把 W' = W + (α/r)·B·A 合进基座，导出成一个普通模型，再按需量化（FP8 / AWQ）。推理和普通模型完全一样，没有额外开销，部署最简单。缺点：每换一版适配器都要重新合并、导出、回归。
                  
      
                  方案 B：vLLM 多 LoRA（按 ISV 定制时用）
                  基座只加载一份，启动时加 --enable-lora --max-loras 10 --max-lora-rank 16，每个请求用 model 字段指定某家 ISV 的适配器。按 r=16、7 个投影层估算，Gemma-2-9B 每个适配器约 5,400 万参数，BF16 约 108 MB，10 家才 1 GB 左右。代价是 LoRA 计算有额外开销、批处理效率略降，要压测。只有当各 ISV 真的需要不同口径或话术时才值得。

                  高频追问（原理 + 工程）
                  
    
                  
    
                  一张纸背下来的核心公式
                  
    
                  前向：     y = W·x + (α/r)·B·A·x          W 冻结；A∈R^(r×d_in)，B∈R^(d_out×r)
参数量：   LoRA = r·(d_in + d_out)   vs   全量 = d_in·d_out      （2048×2048、r=8：32,768 vs 4,194,304，单层 1/128）
初始化：   A 随机、B = 0  → 一开始 ΔW = 0，不改变原模型；第一步 A 的任务梯度为 0
梯度：     ∂L/∂B = s·g·(A·x)ᵀ ；∂L/∂A = s·(Bᵀ·g)·xᵀ ；W 不求权重梯度（但误差仍要穿过它往前传）
损失：     CE = −(1/有效token数)·Σ ln p(正确token)；labels = −100 的位置不计分
步数：     每轮更新次数 ≈ 样本数 ÷ (batch × 累积) = 3375 ÷ 8 ≈ 422；3 轮 ≈ 1,266 次
合并：     W' = W + (α/r)·B·A    （合并后推理零额外开销）
显存：     权重 + KV（2·层·KV头·头维·字节·token·路数）+ 开销  ≤ 显存 × 0.9
