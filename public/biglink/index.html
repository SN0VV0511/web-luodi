Section 01 · Plain Chinese

白话原理：一次请求在 Biglink 里经历了什么？

把 Biglink 想象成一家「代办税务的事务所」：前台（网关）先确认来访的是哪家合作商（ISV）、有没有冒充、今天额度用没用完；接待员（runtime）判断你是来咨询的还是来办事的——咨询就让内部培训过的助理（本地微调模型）直接回答，办事就交给经验更强的顾问（云端大模型）拆成步骤；项目经理（main）把步骤登记成有编号、有状态的工单，并控制预算；外勤（tools 的 Worker）拿着工单去税局窗口（企享云 MCP / 税局通道）办理，同一家企业最多派 2 个外勤，免得把窗口挤爆；凡是要盖章提交的，必须先让会计在草稿上签字（哈希绑定审批）；窗口没回话（超时）时，外勤只去查询结果，绝不重新递交。

① 接入层：谁在调用？

每家 ISV 有 AppKey/AppSecret，请求带 HMAC-SHA256 签名、时间戳和随机数，防伪造和重放；税号必须先经企业授权绑定到该 ISV，跨租户访问一律拒绝；每家 ISV 有独立令牌桶限流。

② 智能层：咨询还是办事？

JEV 分类器把消息分成 chat / business。咨询走本地 LoRA 微调模型（便宜、数据不出内网），办事走云端强模型做结构化规划；规则兜底防止“办事”被误判成“闲聊”。

③ 执行层：怎么办得稳？

工单持久化成 12 态状态机；同税号 2 槽并发；读操作失败可退避重试，最终进死信队列；写操作必须草稿哈希审批、写前登记幂等键，超时进入 outcome_unknown 只对账。

Section 04 · Multi-Tenant Rate Limit & Fair Scheduling

  
10 家 ISV 的令牌桶限流 + 公平调度（实时模拟）

Section 05 · 3-Tier Context Memory

重试与退避（读操作）

  
读接口失败时按指数退避重试：第 k 次等待 min(60s, 2s × 2^(k-1)) × (0.5~1.5 随机抖动)，最多 5 次（约 2+4+8+16+32 = 62s 级别），仍失败就把任务和最后一次错误写进死信队列并告警，由人工或定时任务重放。写操作不走这条路：超时直接进入 outcome_unknown，只能查询对账。

  





  
Section 07 · Tech Stack & Trade-offs

  
技术选型与取舍（面试必问「为什么这么选」）

  

    
层选型备选为什么（取舍）

    
ISV 接入OpenAPI 网关 + HMAC 签名 + 租户隔离 + 令牌桶每家 ISV 单独部署 / OAuth2 授权码只有 10 家 B 端客户，AppKey+签名最简单可审计；时间戳 ±5 分钟 + nonce 去重防重放；每个税号需企业授权后绑定到某个 ISV，查询时 WHERE isv_id=? AND tax_no=? 强制带租户条件。

    
Agent 运行时AgentScope 2.0 + 自研中间件LangChain/LangGraph、Dify、AutoGen需要在模型调用之前用代码做权限校验、配额扣减、意图分流和记忆注入（中间件洋葱圈），而不是写在 Prompt 里；框架轻、方便和自研状态机咬合。

    
模型路由JEV 分类 → 本地 LoRA 模型（咨询）/ 云端大模型（办事）全部云端 / 全部本地大模型咨询类请求占比高、答案模式固定，适合小模型；办事需要长链路 JSON 规划，交给强模型。代价是多维护一个 GPU 服务——按 5,000 税号测算，1 张 48GB 卡即可承载峰值，2 张做 N+1。

    
服务拆分runtime / main / tools 三进程单体 FastAPI模型所在进程不持有税局登录密钥和 MCP 密钥，越狱也拿不到凭据；tools 的 Worker 是子进程，卡死/OOM 不拖垮主服务。

    
任务与队列MySQL 状态机（CAS）+ Redis Streams 队列 + 租约Kafka / Celery / 纯内存5,000 税号、每天几万级任务，Redis Streams 的消费组 + ACK + pending 重领足够；状态真值放 MySQL 保证事务；Kafka 运维成本与规模不匹配，10 倍规模后再考虑。

    
并发控制每税号 2 槽租约 + 每 ISV 令牌桶 + 全局 Worker 池无限协程并发税局侧对同一纳税人并发很敏感，可能锁账号或触发风控；2 槽兼顾吞吐与安全。

    
存储MySQL 8（任务/发票结构化）+ 对象存储（原始报文/版式文件）MongoDB发票去重需要唯一索引（发票代码+号码 / 数电票号）和事务 upsert；原始报文压缩后进对象存储，便于审计回放。

    
可观测结构化日志 + Span 链路 + Prometheus 指标 + 告警只看日志按 requestId/taskId/isvId/taxNo 串联，能回答「某 ISV 某税号昨晚为什么没同步」。

  






  
Section 08 · 24 Engineering Mechanisms

  
24 项 Agent 工程机制（随便挑 3~4 项展开讲）

  

    
🧠 认知与规划
  • JEV 双轨分流：毫秒级区分闲聊/业务，离线降级
  • 结构化意图 + 后置纠偏：Pydantic 校验，关键词兜底防漏判
  • 受控动态重规划：每步根据观测结果生成后续 1~6 步
  • 缺参先追问：没选税号/税期就进入 waiting_user

    
🗂️ 记忆
  • L1 滑窗：最近 8 条原文，4,000 字符上限
  • L2 实体 + 台账投影：0 次额外 LLM 调用
  • L3 偏好：16 项、90 天 TTL
  • 权限烙印：context_only_not_approval

    
🕸️ 多 Agent 协同
  • 6 域 SkillAgent：工商/税务/发票/财务/风险/登录
  • DAG 依赖调度：dependsOn 阻塞与失败级联
  • 子目标独立 intent_mode：只读与草稿分开授权
  • 2 槽租约 + 自然人登录串行锁

    
🛡️ 写安全
  • 12 态 CAS 状态机：status_version 条件更新
  • 草稿 SHA-256 绑定审批 + boundTaskId
  • 写前意图登记 + outcome_unknown 只对账
  • executionVersion 围栏：拒绝僵尸 Worker 回写

    
⚡ 韧性与预算
  • 工具调用指纹去重：tool+规范化参数
  • 无进展检测：连续无变化即中断
  • 半开熔断器：按 domain:upstream 统计，单探测租约
  • 根任务共享预算：Reserve → Settle

    
🔭 可观测与评测
  • Span 链路 + 递归脱敏
  • Pause / Hold / Resume 区分来源
  • 单命令时间线重放（--redact）
  • 三层评测：意图契约 / 闭环回放 / 故障注入自检

  

  
ISV 化之后新增的 4 项（属于接入层）：HMAC 签名 + 防重放、租户隔离查询守卫、每 ISV 令牌桶 + 加权公平调度、读操作指数退避 + 死信队列。






  
Section 09 · Local Model Serving

  
本地微调模型：5,000 个税号要部署多大的卡？

  

    

      
结论先行 估算：按默认假设（日活税号 40%、每个活跃税号每天 8 轮对话、本地模型承接 60%、征期 ×2.5、峰值小时占全天 15%），本地模型峰值约 1 请求/秒，同时在途约 13 路，需要约 250 输出 token/s。

      
    
        
  • 推荐：Gemma-2-9B LoRA 合并后用 FP8（或 AWQ INT4）部署在 1 张 48GB 卡（如 L20）上，峰值够用且留有余量；
    • 
        
  • 高可用：上 2 张（N+1），一张坏了另一张能独立扛住峰值；
    • 
        
  • 预算版：2 张 24GB 卡跑 AWQ INT4，也能扛住，但单卡余量小，长对话多时要限流。
    • 
      

      
原手册里「L20 单卡 60 路并发、1,350 token/s」的说法偏乐观：Gemma-2-9B 每个 token 的 KV 缓存约 0.33 MB（42 层 × 8 个 KV 头 × 256 维 × 2（K 和 V）× 2 字节），2,048 token 的一路对话约 0.69 GB，原文写的 0.34 GB 少算了一半。
